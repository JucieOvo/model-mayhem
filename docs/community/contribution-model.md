# 社区贡献模型

## 目标

把稳定代码、易变内容和对局数值拆成不同的贡献通道，使社区可以通过 Pull Request 提交内容，同时避免频繁更新侃词、图片和数值破坏核心逻辑。

本设计只定义贡献流程、分支职责、自动审查和发行边界，不直接修改现有游戏规则。

## 核心原则

1. 核心逻辑与易变内容分离。
2. 社区 PR 只进入对应集成分支，不直接写 `main`。
3. 自动检查负责发现结构错误和明显失衡，人类审查负责判断创意、语境和审美。
4. 内容包必须声明版本、引擎兼容范围和内容哈希。
5. 已发布内容必须可追溯、可回滚、可复现。
6. 不把长期变化内容堆积到无限数量的永久分支中。

## 分支结构

建议采用以下有界分支模型：

```text
main
  核心代码、规则引擎、数据模式、基础内容包

content/next
  侃词、卡面、缩略图、多媒体和世界事件内容的社区集成分支

content/stable
  当前稳定内容包分支，只允许发行负责人更新

balance/next
  卡牌数值、研究成本、资源曲线和预组平衡建议的集成分支

balance/stable
  当前稳定平衡包分支，只允许平衡负责人更新

updates/stable
  面向玩家更新器的稳定真源，由发行任务从 stable 分支生成

updates/beta
  面向测试版玩家的真源，包含 next 分支已经通过审查的内容

updates/experimental
  面向实验版玩家的真源，可以包含尚未进入稳定包的数值和内容

release/content-vYYYY.MM.N
release/balance-vYYYY.MM.N
  可选发行分支，用于需要长期维护的版本线
```

社区提交时在个人 Fork 中创建短生命周期分支：

```text
pr/banter/<topic>
pr/media/<topic>
pr/event/<topic>
pr/balance/<topic>
```

提交完成后：

```text
社区短分支
    |
    v
content/next 或 balance/next    社区初审
    |
    v
content/stable 或 balance/stable    项目所有者合入
    |
    v
updates/stable、不可变标签与内容发行包
```

不长期保留每次更新的独立工作分支。需要保留的版本使用标签或发行分支，避免分支数量随版本数量无限增长。

## 内容边界

### `main`

`main` 只承载以下内容：

- 游戏引擎和规则解释器。
- API、工具协议和内容结构模式。
- 内容加载、校验、更新和回滚逻辑。
- 一份最小基础内容包，保证离线首次启动可用。
- 与引擎强绑定的新内容类型。

`main` 允许出现破坏性更新。任何内容包在合并前必须声明它所支持的最小和最大引擎版本。

### `content/next` 与 `content/stable`

这两个分支承载容易变化且通常不改变引擎行为的内容：

- 侃词、描述和广播文本。
- 卡面插画、缩略图和界面素材。
- 世界事件文案。
- 活动和赛季主题。
- 不影响规则解释器的展示字段。

内容分支不修改 `apps/`、`packages/` 或服务端行为。

### `balance/next` 与 `balance/stable`

这两个分支承载需要模拟和审查的数值内容：

- 卡牌费用和资源消耗。
- 效果强度、触发次数和持续时间。
- 研究节点成本与前置关系。
- 预组构筑和阵营平衡参数。
- 胜利进度和回合节奏参数。

平衡分支不修改代码。需要新效果或新字段时，先向 `main` 提交引擎能力，再在平衡分支使用该字段。

## 内容包结构

建议每个发行内容包包含独立清单：

```text
content-packs/
  content/
    v2026.09.1/
      manifest.json
      cards/
      banter/
      events/
      assets/
  balance/
    v2026.09.1/
      manifest.json
      balance/
      decks/
      research/
```

清单至少声明：

```json
{
  "packId": "content-v2026.09.1",
  "packType": "content",
  "schemaVersion": 1,
  "minEngineVersion": "0.2.0",
  "maxEngineVersion": "0.3.x",
  "contentHash": "sha256:...",
  "createdAt": "2026-09-13T00:00:00Z",
  "sourceCommit": "git-commit"
}
```

游戏更新器只安装清单完整、哈希一致且引擎版本兼容的内容包。

## 社区 Pull Request 流程

### 内容和多媒体贡献

贡献者提交：

1. 新增或修改的内容文件。
2. 来源、作者、许可证和权利状态。
3. 目标展示位置和使用场景。
4. 图片原始尺寸、裁切安全区和缩略图。
5. 是否引用现实人物、公司、产品或受保护素材。
6. 贡献者签署来源真实性声明。

自动审查通过后，进入 `content/next`。

### 数值平衡贡献

贡献者提交：

1. 目标内容 ID 和当前值。
2. 建议值和修改理由。
3. 受影响的构筑、策略或阵营。
4. 固定种子和样本数量。
5. 模拟结果、对照组和置信区间。
6. 已知风险和反例。

自动审查通过后，进入 `balance/next`。

## 自动审查

### 内容审查

`content-review` 负责：

- YAML、JSON 和资源清单结构校验。
- 引用完整性校验，包括卡牌、组织、模型、技术、事件和资源路径。
- 图片格式、分辨率、透明通道、文件大小和安全区校验。
- 图片哈希、感知哈希和重复素材检测。
- 侃词长度、语言、重复度和相似文本检测。
- 目标对象和可能的事实声明提取。
- 受保护人物、品牌、版权和敏感内容风险标记。
- 生成结构化的审查报告，供维护者快速判断。

自动审查不批准创意内容，只降低人工检查成本。

### 平衡审查

`balance-review` 负责：

- 使用固定随机种子运行基线卡组和对局。
- 比较改动前后的胜率、平均对局长度、资源转化率和关键牌出现率。
- 检测单一策略占比、先手优势和组合技异常。
- 生成样本量、置信区间和差异摘要。
- 对明显越界的结果直接阻止合并。

建议的默认阈值如下，最终数值必须配置化：

| 状态 | 判定条件 | 处理 |
|---|---|---|
| 绿色 | 胜率变化不超过 3%，且无策略垄断 | 可进入人工审查 |
| 黄色 | 胜率变化为 3% 到 7%，或指标异常 | 需要平衡负责人复核 |
| 红色 | 胜率变化超过 7%，组合技或策略占比严重异常 | 阻止合并，必要时启动专项模拟 |

阈值只是审查触发器，不是自动平衡结论。

## 维护者控制

社区贡献者只能提交 Pull Request，不得直接写入 `main`、`content/stable`、
`balance/stable`、`updates/*` 或发行标签。项目所有者 JucieOvo 保留以下独占权限：

- 审核并合入社区 Pull Request。
- 决定哪些内容进入 `main`。
- 决定哪些内容和数值进入稳定版本。
- 触发发行标签和更新器真源发布。
- 处理回滚、撤回和兼容性冲突。

即使自动检查全部通过，也不代表贡献已经获得合并或发行许可。

## 人类审查职责

### 内容审查员

负责判断：

- 文案是否符合项目语气。
- 调侃是否针对行业现象而不是个人。
- 图片是否适配卡面和界面裁切。
- 来源声明是否可信。
- 是否适合当前稳定频道。

### 平衡审查员

负责判断：

- 数值改动是否符合目标环境。
- 模拟样本是否足以支撑结论。
- 是否存在未被指标捕获的体验问题。
- 是否需要伴随式内容说明或补偿。

### 项目所有者

负责：

- 合并 `next` 到 `stable`。
- 生成不可变内容包和标签。
- 更新 `updates/*` 真源分支。
- 更新发行说明。
- 触发玩家端可用更新。
- 在异常时执行回滚。

当前阶段由 JucieOvo 同时承担核心审查、内容审查、平衡审查和发行职责。后续即使增加
审查员，也只能提供审查意见，不能获得稳定分支和发行标签的最终合并权限，除非项目所有者
明确授权。

## 分支保护

建议为公开仓库配置：

```text
main
  必须通过 core-verify
  必须至少一名核心维护者批准
  禁止直接推送

content/next
  必须通过 content-verify
  社区提交 PR，项目所有者决定是否合入

balance/next
  必须通过 balance-verify
  社区提交 PR，项目所有者决定是否合入

content/stable 和 balance/stable
  只允许项目所有者合并
  必须通过兼容性和发行检查

updates/*
  只允许发行工作流写入
  禁止社区直接推送
```

`CODEOWNERS` 应分别指定核心、内容、平衡和发行责任人。

## 许可和来源

代码贡献继续使用项目根许可证。内容贡献应使用单独的内容许可证，并由贡献者在 PR 中确认。

建议：

- 代码和规则：Apache-2.0。
- 原创侃词、原创插图和原创多媒体：CC BY 4.0。
- 第三方素材：必须在 PR 中声明来源、作者、许可证和可再分发依据。
- 不接受没有来源和授权说明的第三方图片。

内容许可证最终选择需要在正式开放贡献前确定。

## 发布与更新

### 更新器真源

更新器不从社区 PR 分支直接读取内容，而是从项目所有者发布的 `updates/*` 真源读取。

建议的通道关系：

| 玩家通道 | 更新分支 | 内容来源 |
|---|---|---|
| stable | `updates/stable` | `content/stable` 和 `balance/stable` |
| beta | `updates/beta` | `content/next` 和 `balance/next` 中已通过审查的内容 |
| experimental | `updates/experimental` | 项目所有者指定的实验内容 |

`updates/*` 是单向生成分支，不接受社区直接提交。内容贡献仍然只通过对应 `next` 分支
的 Pull Request 进入。

稳定频道只读取 `content/stable` 和 `balance/stable` 对应的不可变内容包。

测试频道可以读取 `content/next` 和 `balance/next`，但必须在界面中明确标记为测试内容。

更新过程：

1. 下载内容包和清单。
2. 校验清单、哈希和引擎兼容范围。
3. 暂存到新的版本目录。
4. 切换活动版本指针。
5. 保留 A-B-C 回滚窗口。

内容更新不得包含程序代码、数据库迁移或任意可执行脚本。

### 现有更新器能力

当前 `packages/content-updater` 已经具备：

- 通过 Git 提交读取远端内容分支。
- 只检出单一内容路径，不加载完整仓库。
- 校验内容清单、目录树哈希和数据库结构兼容性。
- 使用 A-B-C 单回滚点保存玩家数据。
- 检测系统内容被本地修改后停止官方更新。
- 以锁定文件阻止并发更新事务。

### 需要补充的更新器能力

为满足集中控制和真源更新，还需要：

1. 将默认更新分支从 `main` 改为 `updates/stable`。
2. 支持同时读取内容和平衡两个内容包，或由发行任务先合并为单一稳定内容包。
3. 对内容清单增加签名，更新器内置公钥验证。
4. 增加版本单调检查，拒绝旧版本覆盖新版本。
5. 增加允许的仓库、分支和标签模式校验，防止把用户内容源替换为任意远端。
6. 在更新状态中分别展示代码版本、内容版本和平衡版本。
7. 为 stable、beta 和 experimental 建立独立真源。
8. 在发行任务中生成更新说明、内容差异和回滚目标。

其中第一项和第四至第六项属于代码变更，需要单独实施和验证，不在本设计文档中直接修改。

## 分阶段实施

### 第一阶段

- 建立分支和 `CODEOWNERS`。
- 增加内容与平衡 PR 模板。
- 增加基础结构和引用校验。
- 建立内容包清单格式。

### 第二阶段

- 增加侃词重复度和来源检查。
- 增加图片尺寸、重复素材和风险标记。
- 增加确定性平衡模拟报告。
- 建立稳定频道和测试频道。

### 第三阶段

- 将内容包发行接入玩家端更新器。
- 增加签名、回滚和兼容性门禁。
- 根据真实贡献数据调整审查阈值。
