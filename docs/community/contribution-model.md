# 社区贡献模型

## 目标

把稳定代码、易变内容和对局数值拆成不同的贡献通道，使社区可以通过 Pull Request 提交内容，同时避免频繁更新侃词、图片和数值破坏核心逻辑。

本文档定义贡献流程、分支职责、审查要求和发行边界，不直接修改现有游戏规则。

## 核心原则

1. 核心逻辑与易变内容分离。
2. 社区 PR 只进入对应集成分支，不直接写 `main`。
3. 自动检查负责发现结构错误和明显失衡，人类审查负责判断创意、语境和审美。
4. 内容包必须声明内容版本和规则版本；内容哈希由发行流程根据真实目录生成。
5. 已发布内容必须可追溯、可回滚、可复现。
6. 不把长期变化内容堆积到无限数量的永久分支中。

## 分支结构

当前采用以下有界分支模型：

```text
main
  核心代码、规则引擎、数据模式、基础内容包

content/next
  侃词、卡面、缩略图、多媒体和世界事件内容的孤立社区集成分支

content/stable
  当前稳定内容包的孤立快照分支，只允许发行负责人更新

balance/next
  卡牌数值、研究成本、资源曲线和预组平衡建议的孤立集成分支

balance/stable
  当前稳定平衡包的孤立快照分支，只允许平衡负责人更新

custom
  由使用者显式配置的来源，不属于官方稳定或预览通道

release/content-vYYYY.MM.N
release/balance-vYYYY.MM.N
  可选发行分支，用于需要长期维护的版本线
```

社区提交时在个人 Fork 中创建短生命周期分支：

```text
pr/banter/<topic>
pr/media/<topic>
pr/event/<topic>
pr/balance/<topic>
```

提交完成后：

```text
社区短分支
    |
    v
content/next 或 balance/next    社区初审
    |
    v
content/stable 或 balance/stable    项目所有者写入快照

上述稳定分支同时是玩家更新器的读取源。发行时只更新对应真源，并生成不可变标签与
内容发行清单，不再维护额外的合并分支。
```

四个数据分支均以独立根提交建立，与 `main` 没有共同祖先。`next` 审核通过后，
维护者把受管目录写入 `stable` 的新快照提交，不执行普通 merge。因此数据分支只包含
自身职责下的 `content/` 目录，不会重新带回完整程序本体。

不长期保留每次更新的独立工作分支。需要保留的版本使用标签或发行分支，避免分支数量随版本数量无限增长。

## 内容边界

### `main`

`main` 只承载以下内容：

- 游戏引擎和规则解释器。
- API、工具协议和内容结构模式。
- 内容加载、校验、更新和回滚逻辑。
- 一份最小基础内容包，保证离线首次启动可用。
- 与引擎强绑定的新内容类型。

`main` 允许出现破坏性更新。任何内容包在合并前必须使用目标引擎完整校验，并记录
`rulesetVersion` 和平衡包标识；最小与最大引擎版本范围是后续显式兼容性能力。

### `content/next` 与 `content/stable`

这两个分支承载容易变化且通常不改变引擎行为的内容：

- 侃词、描述和广播文本。
- 卡面插画、缩略图和界面素材。
- 世界事件文案。
- 活动和赛季主题。
- 不影响规则解释器的展示字段。

内容分支不修改 `apps/`、`packages/` 或服务端行为。

`content/*` 的实际提交树只包含：

```text
content/manifest/
content/presentation/
content/questions/
content/thumbnails/
```

### `balance/next` 与 `balance/stable`

这两个分支承载需要模拟和审查的数值内容：

- 卡牌费用和资源消耗。
- 效果强度、触发次数和持续时间。
- 研究节点成本与前置关系。
- 预组构筑和阵营平衡参数。
- 胜利进度和回合节奏参数。

平衡分支不修改代码。需要新效果或新字段时，先向 `main` 提交引擎能力，再在平衡分支使用该字段。

`balance/*` 的实际提交树只包含：

```text
content/manifest/
content/cards/
content/balance/
content/decks/
content/research/
content/eras/
content/doctrines/
```

## 内容包结构

每个发行内容包包含独立清单：

```text
content-packs/
  content/
    v2026.09.1/
      manifest.json
      cards/
      banter/
      events/
      assets/
  balance/
    v2026.09.1/
      manifest.json
      balance/
      decks/
      research/
```

当前内容清单位于 `content/manifest/`，使用 YAML 声明：

```yaml
id: model-mayhem-reference
version: 0.2.1
rulesetVersion: 0.2.1
balanceId: standard-v0.1
```

内容树哈希由更新器对真实目录生成，来源提交由 Git 真源记录。更新器只暂存能够
通过当前内容加载器完整校验、且目录树哈希一致的内容。

## 社区 Pull Request 流程

### 内容和多媒体贡献

贡献者提交：

1. 新增或修改的内容文件。
2. 来源、作者、许可证和权利状态。
3. 目标展示位置和使用场景。
4. 图片原始尺寸、裁切安全区和缩略图。
5. 是否引用现实人物、公司、产品或受保护素材。
6. 贡献者签署来源真实性声明。

审查通过后，由维护者合入 `content/next`。

### 数值平衡贡献

贡献者提交：

1. 目标内容 ID 和当前值。
2. 建议值和修改理由。
3. 受影响的构筑、策略或阵营。
4. 固定种子和样本数量。
5. 模拟结果、对照组和置信区间。
6. 已知风险和反例。

审查通过后，由维护者合入 `balance/next`。

## 审查要求

### 内容审查

内容贡献在合入前检查：

- YAML、JSON 和资源清单结构校验。
- 引用完整性校验，包括卡牌、组织、模型、技术、事件和资源路径。
- 图片格式、分辨率、透明通道、文件大小和安全区校验。
- 图片哈希、感知哈希和重复素材检测。
- 侃词长度、语言、重复度和相似文本检测。
- 目标对象和可能的事实声明提取。
- 受保护人物、品牌、版权和敏感内容风险标记。
- 生成结构化的审查报告，供维护者快速判断。

自动审查不批准创意内容，只降低人工检查成本。

### 平衡审查

数值贡献在合入前检查：

- 使用固定随机种子运行基线卡组和对局。
- 比较改动前后的胜率、平均对局长度、资源转化率和关键牌出现率。
- 检测单一策略占比、先手优势和组合技异常。
- 生成样本量、置信区间和差异摘要。
- 对明显越界的结果直接阻止合并。

当前复核阈值如下，最终数值必须配置化：

| 状态 | 判定条件 | 处理 |
|---|---|---|
| 绿色 | 胜率变化不超过 3%，且无策略垄断 | 可进入人工审查 |
| 黄色 | 胜率变化为 3% 到 7%，或指标异常 | 需要平衡负责人复核 |
| 红色 | 胜率变化超过 7%，组合技或策略占比严重异常 | 阻止合并，必要时启动专项模拟 |

阈值只是审查触发器，不是自动平衡结论。

## 维护者控制

社区贡献者只能提交 Pull Request，不得直接写入 `main`、`content/stable`、
`balance/stable` 或发行标签。项目所有者 JucieOvo 保留以下独占权限：

- 审核并合入社区 Pull Request。
- 决定哪些内容进入 `main`。
- 决定哪些内容和数值进入稳定版本。
- 触发发行标签和更新器真源发布。
- 处理回滚、撤回和兼容性冲突。

即使自动检查全部通过，也不代表贡献已经获得合并或发行许可。

## 人类审查职责

### 内容审查员

负责判断：

- 文案是否符合项目语气。
- 调侃是否针对行业现象而不是个人。
- 图片是否适配卡面和界面裁切。
- 来源声明是否可信。
- 是否适合当前稳定频道。

### 平衡审查员

负责判断：

- 数值改动是否符合目标环境。
- 模拟样本是否足以支撑结论。
- 是否存在未被指标捕获的体验问题。
- 是否需要伴随式内容说明或补偿。

### 项目所有者

负责：

- 合并 `next` 到 `stable`。
- 生成不可变内容包和标签。
- 维护 `content/stable` 和 `balance/stable` 两个真源分支。
- 更新发行说明。
- 触发玩家端可用更新。
- 在异常时执行回滚。

当前阶段由 JucieOvo 同时承担核心审查、内容审查、平衡审查和发行职责。后续即使增加
审查员，也只能提供审查意见，不能获得稳定分支和发行标签的最终合并权限，除非项目所有者
明确授权。

## 分支保护

公开仓库的分支权限规则如下：

```text
main
  必须通过 core-verify
  必须至少一名核心维护者批准
  禁止直接推送

content/next
  必须通过 content-verify
  社区提交 PR，项目所有者决定是否合入

balance/next
  必须通过 balance-verify
  社区提交 PR，项目所有者决定是否合入

content/stable 和 balance/stable
  只允许项目所有者合并
  必须通过兼容性和发行检查
```

`CODEOWNERS` 应分别指定核心、内容、平衡和发行责任人。

## 许可和来源

代码贡献继续使用项目根许可证。内容贡献应使用单独的内容许可证，并由贡献者在 PR 中确认。

建议：

- 代码和规则：Apache-2.0。
- 原创侃词、原创插图和原创多媒体：CC BY 4.0。
- 第三方素材：必须在 PR 中声明来源、作者、许可证和可再分发依据。
- 不接受没有来源和授权说明的第三方图片。

内容许可证最终选择需要在正式开放贡献前确定。

## 发布与更新

### 更新器真源

更新器不从社区 PR 分支直接读取内容，而是分别从项目所有者维护的 `content/*` 和
`balance/*` 真源读取。

建议的通道关系：

| 玩家通道 | 卡面分支 | 数值分支 |
|---|---|---|
| stable | `content/stable` | `balance/stable` |
| preview | `content/next` | `balance/next` |
| custom | 使用者配置 | 使用者配置 |

稳定分支只接受项目所有者的发行合并，不接受社区直接提交。内容贡献仍然只通过对应
`next` 分支的 Pull Request 进入。

### 分支静态查看器

`content/next` 和 `balance/next` 各自保存一个自包含的 `preview.html`：

```text
content/next/preview.html
balance/next/preview.html
```

查看器从当前分支的真实 `content/` 目录、来源清单和缩略图生成，不引用 `main` 文件，
也不在运行时请求网络。内容审核者可以直接双击打开并搜索、筛选和查看详情。

修改分支数据后必须重新生成：

```powershell
pnpm preview:community -- --root <分支工作树>
pnpm preview:community -- --root <分支工作树> --check
```

`preview.html` 是生成产物，不接受手工修改。数据 PR 未同步查看器时，不得进入
`stable`。

稳定频道分别读取 `content/stable` 和 `balance/stable`，在玩家设备上组合为一个完整内容包。

测试频道可以读取 `content/next` 和 `balance/next`，但必须在界面中明确标记为测试内容。

默认路径归属如下，两个来源不能声明重叠目录：

| 来源 | 默认受管路径 |
|---|---|
| 卡面内容 | `presentation/`、`thumbnails/`、`questions/` |
| 数值内容 | `cards/`、`balance/`、`decks/`、`research/`、`eras/`、`doctrines/` |

来源清单只用于读取版本和兼容信息，不直接互相覆盖；更新器会根据两个来源的清单生成本地
组合清单，再由现有内容加载器完成最终校验。

更新过程：

1. 分别读取卡面源和数值源的最新提交。
2. 校验两个来源的清单、引用关系、来源路径哈希和数据库结构兼容性。
3. 在本地临时目录中按受管路径组合内容，不生成远端合并分支。
4. 对组合目录执行完整内容校验和目录树哈希校验。
5. 两边都成功后只切换一次活动版本指针，并保留 A-B-C 回滚窗口。

内容更新不得包含程序代码、数据库迁移或任意可执行脚本。

### 现有更新器能力

当前 `packages/content-updater` 已经具备：

- 通过 Git 提交分别读取卡面分支和数值分支。
- 只检出两个来源各自的受管路径和来源清单，不加载完整仓库。
- 使用当前内容加载器校验清单、引用关系和规则结构。
- 分别校验两个来源路径哈希、来源清单和组合目录树哈希。
- 使用 A-B-C 单回滚点保存玩家数据。
- 检测系统内容被本地修改后停止官方更新。
- 以锁定文件阻止并发更新事务。

### 更新器当前限制

更新器已经完成卡面源与数值源的拆分，但对安装目录仍执行完整内容校验、目录树哈希校验和
数据库结构校验。最小与最大引擎版本范围、清单签名和发行差异报告尚未接入，不能把这些
能力描述为现有保证。
